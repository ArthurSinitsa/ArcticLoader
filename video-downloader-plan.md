# Self-hosted сервис скачивания видео — архитектура и план реализации

Документ собирает выводы обсуждения: оценку идеи, архитектурные решения, стек и
поэтапный роадмап.

---

## 1. Выводы по идее

### 1.1. Движок писать не нужно

Изначальная задумка — вытягивание ссылок, поиск плейлистов (включая JSON),
поддержка YouTube / VK / OK / FB / IG, generic-режим для неизвестных сайтов —
это функциональное описание **yt-dlp**: ~1800 экстракторов, generic-extractor,
находящий `<video>`, HLS/DASH-манифесты и JSON-плейлисты на произвольной
странице.

Вывод: **свои экстракторы не пишем**. Ценность проекта — в сервисном слое:
удобный доступ с любого устройства, очередь, история, лимиты, хранилище.

Что стоит изучить перед стартом:

| Проект | Чем полезен |
|---|---|
| MeTube | минимальный веб-UI поверх yt-dlp, референс простоты |
| Pinchflat | подписки и автозагрузка, работа с расписанием |
| yt-dlp-web-ui | близкий по духу self-hosted вариант |
| cobalt (imput) | публичный сервис — видно, во что упирается такая архитектура |

### 1.2. Главный риск — не нагрузка, а поддержка

Площадки активно сопротивляются: YouTube меняет расшифровку сигнатур и
требования к токенам раз в несколько недель. Ломается всё сразу и у всех.
У yt-dlp сотни контрибьюторов именно поэтому — один человек такой темп не держит.

Практический вывод: обёртка + автообновление движка. План «сломалось — допилю
сам» работает для UI-слоя, но не для парсеров.

### 1.3. Второй риск — IP-репутация

Датацентровые адреса (любой VPS) площадки вычисляют и режут быстро: капчи,
пустые ответы, требования подтвердить, что ты не бот. Домашний / офисный IP
живёт несравнимо дольше. Это самостоятельный аргумент за размещение на своём
железе, а не в облаке.

### 1.4. FFmpeg дешевле, чем кажется; трафик дороже

Объединение видео- и аудиодорожки из DASH — это **ремукс** (`-c copy`), без
перекодирования: 10 минут 1080p сшиваются за секунды, упор в диск, а не в CPU.

| Операция | Стоимость |
|---|---|
| Ремукс (`-c copy`) | секунды, ~0 CPU |
| Перекодирование (VP9/AV1 → H.264) | ~реальное время на ядро и хуже |
| Трафик | 1080p/10 мин ≈ 150–300 МБ, ×2 (принять + отдать) |

Перекодирование по умолчанию **не включаем никогда** — только по явному запросу
пользователя и с отдельным низкоприоритетным лимитом.

### 1.5. Ключевая оптимизация

Если yt-dlp нашёл формат, где видео и звук уже в одном контейнере
(progressive), сервер **не участвует в передаче** — клиенту отдаётся прямая
ссылка на CDN источника. Канал сервера расходуется только там, где реально
нужен ремукс. На практике это отсекает больше половины запросов.

Для оставшихся — стриминг без промежуточного файла:
`yt-dlp → ffmpeg → HTTP-ответ` фрагментированным MP4.

## 2. Архитектура

### 2.1. Компоненты

| Компонент | Роль |
|---|---|
| **Caddy** | TLS, отдача готовых файлов с диска мимо Python |
| **FastAPI** | только быстрые операции: авторизация, приём URL, статус, SSE |
| **Redis** | брокер очереди ARQ + pub/sub канал прогресса |
| **Worker-пул (ARQ)** | 2–4 процесса, каждый дёргает yt-dlp / ffmpeg |
| **PostgreSQL** | пользователи, задачи, история, кэш метаданных |
| **Cron-задачи** | обновление yt-dlp, чистка файлов, канареечные проверки |

### 2.2. Поток обработки запроса

```
Клиент (PWA)
     │  POST /api/downloads  { url, format }
     ▼
FastAPI ──► проверка лимитов ──► задача в очередь Redis ──► 202 + task_id
     │
     ▼
Worker + yt-dlp ──► извлечение метаданных
     │
     ├──► формат готов (progressive)
     │        └─► прямая ссылка на CDN источника → клиент качает сам
     │            [нагрузка на сервер ≈ 0]
     │
     └──► нужен ремукс (DASH: видео + аудио раздельно)
              └─► ffmpeg -c copy ──► файл на диске ──► Caddy отдаёт клиенту

Прогресс во всех ветках: progress_hooks → Redis pub/sub → SSE → клиент
```

### 2.3. Обоснование выбора технологий

**FastAPI, не DRF.** Нагрузка I/O-bound (сеть, стриминг, живой прогресс) —
async выигрывает у синхронного DRF на порядок по числу одновременных соединений
на слабом железе. Плюс автогенерируемый OpenAPI-контракт для будущих мобильных
клиентов. DRF оправдан, когда нужна вся экосистема Django (админка, ORM,
готовая аутентификация) — здесь это не критично.

**ARQ, не Celery.** Async-native, конфиг в десяток строк, ложится на FastAPI
без прослоек. Redis всё равно нужен для pub/sub, второй сущности не появляется.
Celery мощнее, но тяжелее и синхронный по духу.

**PostgreSQL, не SQLite.** Несколько воркеров пишут прогресс параллельно, а
SQLite блокируется на запись целиком. Postgres съест 100–200 МБ и снимет класс
проблем навсегда.

**SSE, не WebSocket.** Поток односторонний, переподключение браузер делает сам,
проходит через любой прокси. Троттлинг — не чаще одного события в секунду,
иначе Redis захлебнётся апдейтами от ffmpeg.

**React + Vite + TS + Tailwind + shadcn/ui**, состояние — TanStack Query.
Обязательно **PWA** (`vite-plugin-pwa`): ставится на домашний экран телефона и
выглядит как приложение, что откладывает нативные клиенты на неопределённый
срок без потери удобства. Альтернатива — SvelteKit: меньше кода, легче бандл,
беднее экосистема.

### 2.4. Модель данных

```
users          id, email, name, telegram_id, password_hash, role_id,
               must_change_password, is_active, created_at, last_login_at

roles          id, code, title, is_unlimited
               -- guest / user / admin / superadmin

quota_profiles role_id, daily_limit, concurrent_limit,
               bucket_capacity, bucket_refill_minutes
               -- лимиты редактируются из админки, не зашиты в код

tasks          id, user_id (nullable для гостя), guest_fingerprint,
               source_url, extractor, format_id, status, progress,
               worker_pid, error_code, file_path, file_size,
               expires_at, created_at, finished_at

playlists      id, user_id, title, created_at
playlist_items playlist_id, source_url, title, position

media_cache    cache_key (hash от url+format), file_path, expires_at, hits
url_meta       url_hash, extractor, formats_json, fetched_at  -- TTL 15–30 мин

registration_requests  id, telegram_id, telegram_username, email, name,
                       status, processed_by, processed_at, created_at

audit_log      id, actor_id, action, target_type, target_id,
               payload_json, ip, created_at
```

`status`: `queued → extracting → downloading → processing → ready`
плюс терминальные `failed`, `cancelled`, `expired`.

`worker_pid` нужен для принудительного прерывания задачи админом — см. 2.5.3.

### 2.5. Роли и права доступа

#### 2.5.1. Матрица возможностей

| Возможность | Гость | Пользователь | Админ | Суперадмин |
|---|:---:|:---:|:---:|:---:|
| Скачивание | ✓ | ✓ | ✓ | ✓ |
| История загрузок | — | ✓ | ✓ | ✓ |
| Сохранённые плейлисты | — | ✓ | ✓ | ✓ |
| Отмена своей задачи | — | ✓ | ✓ | ✓ |
| Раздел «Администрирование» | — | — | ✓ | ✓ |
| Список пользователей, фильтры, сортировка | — | — | ✓ | ✓ |
| Создание учётной записи | — | — | ✓ | ✓ |
| Удаление учётной записи | — | — | ✓ | ✓ |
| Просмотр активных задач всех пользователей | — | — | ✓ | ✓ |
| Прерывание чужих задач | — | — | ✓ | ✓ |
| Изменение ролей и квот | — | — | — | ✓ |
| Управление админами | — | — | — | ✓ |
| Глобальные настройки, «рубильник» | — | — | — | ✓ |
| Просмотр журнала аудита | — | — | — | ✓ |

Админ не может повышать роли и трогать других админов — иначе разделение
уровней теряет смысл: любой админ становится суперадмином за два клика.

#### 2.5.2. Квоты

| Роль | В сутки | Параллельно | Пачка | Интервал восполнения |
|---|---:|---:|---:|---:|
| Гость | 5 | 1 | 1 | 30 мин |
| Пользователь | 16 | 4 | 4 | 20 мин |
| Админ | 24 | 4 | 4 | 10 мин |
| Суперадмин | ∞ | ∞ | ∞ | — |

Механика — **token bucket в Redis**: ёмкость = размер пачки, восполнение
по таймеру. Одна реализация покрывает все роли; суперадмин просто обходит
проверку по флагу `is_unlimited`.

Ключ ведра: `bucket:user:{id}` для авторизованных, `bucket:guest:{fingerprint}`
для гостей. Отдельно — суточный счётчик с TTL до полуночи.

#### 2.5.3. Прерывание задач

Недостаточно снять job с очереди — yt-dlp и ffmpeg работают как дочерние
процессы. Порядок:

1. Пометить задачу `cancelled` в БД (воркер проверяет флаг между шагами)
2. Отправить `SIGTERM` процессу по сохранённому `worker_pid`
3. Через 5 секунд — `SIGKILL`, если не завершился
4. Удалить частично скачанные файлы (`.part`, `.ytdl`, временные потоки)
5. Вернуть токен в ведро, если задача не начала расходовать трафик
6. Запись в `audit_log`

Отмена своей задачи пользователем использует тот же механизм.

### 2.6. Регистрация и вход

Публичной формы регистрации нет. Кнопка «Регистрация» открывает модальное
окно с объяснением и кнопкой перехода в Telegram-бота.

```
Пользователь → /start у бота
             → бот спрашивает email (обязательно), имя (если не указано,
               берётся из профиля Telegram)
             → заявка падает в registration_requests
             → админу уведомление в Telegram
             → админ одобряет из веб-админки или прямо из бота
             → бот присылает пользователю логин и временный пароль
             → первый вход → принудительная смена пароля
```

Детали, которые легко упустить:

- **Временный пароль живёт 48 часов.** Не активировали — заявка сгорает,
  учётка не создаётся.
- **`must_change_password`** блокирует все эндпоинты, кроме смены пароля.
- **`telegram_id` привязывается к учётке** — это даёт бесплатный канал для
  сброса пароля и уведомлений о готовности файлов.
- **Email нужен для восстановления доступа**, если Telegram потерян.
  Подтверждение письмом на первом этапе избыточно — админ и так проверяет
  заявку вручную.
- **Защита от перебора на входе**: 5 неудачных попыток → блокировка на
  15 минут по связке IP + логин. Иначе открытая форма входа на публичном
  адресе живёт до первого сканера.

### 2.7. Выбор качества

**Почему это не мелочь UI.** Селектор по умолчанию `bv*+ba/b` означает «лучшее
из доступного». Для десятиминутного ролика в 4K AV1 это ~720 МБ, которые сервер
сначала принимает, а потом отдаёт — 1.4 ГБ канала на одну загрузку, которую
пользователь почти наверняка смотрел бы в 1080p. Умолчание «максимум» —
самая дорогая настройка во всём сервисе.

**Профили, а не сырые селекторы.** Пользователю нельзя показывать
`bv*[height<=1080]+ba/b` — это синтаксис yt-dlp, и он же открывает произвольное
выражение в API. Наружу отдаём фиксированный набор:

| Профиль | Селектор | Комментарий |
|---|---|---|
| `audio` | `ba/b` | только звук, Этап 10 |
| `360p` | `bv*[height<=360]+ba/b[height<=360]` | мобильный интернет |
| `720p` | `bv*[height<=720]+ba/b[height<=720]` | |
| `1080p` | `bv*[height<=1080]+ba/b[height<=1080]` | **по умолчанию** |
| `max` | `bv*+ba/b` | 4K и выше, по явному выбору |

Кодек тоже стоит ограничивать: AV1 и VP9 весят меньше, но AV1 не проигрывается
на части устройств и телевизоров. Предпочтение H.264 при прочих равных
(`vcodec:h264` в `--format-sort`) избавляет от жалоб «скачалось, но не
открывается».

**Список форматов для выпадающего списка.** `GET /api/formats?url=…` возвращает
доступные профили с разрешением и приблизительным размером — размер до
скачивания и есть главная причина, по которой список нужен живой, а не
захардкоженный: у конкретного ролика может не быть 1080p вовсе.

Ответ кэшируется в `url_meta` на 15–30 минут (раздел 3.1): открытие выпадающего
списка не должно стоить обращения к площадке, иначе один пользователь,
перебирающий варианты, тратит IP-репутацию за всех.

## 3. Отказоустойчивость: лимиты на всех уровнях

Принцип: сервис защищается **ограничениями, а не масштабированием**. Ноутбук
физически не может качать 20 потоков — лучше пусть 17 человек ждут в очереди,
чем все 20 получают по 300 КБ/с и таймауты.

| Слой | Ограничение |
|---|---|
| Глобально | 4–6 одновременных загрузок независимо от суммы пользовательских квот |
| На роль | token bucket по таблице 2.5.2 |
| Гостевой доступ | Turnstile-проверка + «рубильник» отключения (см. 3.6) |
| Диск | проверка свободного места **до** старта задачи; ниже порога — пауза очереди |
| Задача | таймаут 30 мин, лимит размера, максимум 2 ретрая с backoff |
| Файлы | TTL 24–48 ч, cron-чистка |
| API | rate limit на создание задач, отдельный — на вход |

Обрати внимание на первую строку: если пять пользователей одновременно имеют
право на 4 параллельные загрузки, это не значит, что сервер должен тянуть 20.
Глобальный семафор стоит **выше** ролевых квот и просто удерживает лишнее в
очереди.

### 3.1. Кэш

Ключ `(url, format_id)`. Семья и друзья качают одно и то же — если файл ещё жив
на диске, отдаём мгновенно, ноль нагрузки. Метаданные (список форматов)
кэшируются отдельно на 15–30 минут: экономит обращения к площадкам и бережёт IP.

### 3.2. Канареечные проверки

Cron раз в час прогоняет `yt-dlp --simulate` по эталонному списку из 5–7 ссылок
(YouTube, VK, OK, прямой MP4, HLS-поток). Сломалось — алерт в Telegram. Ты
узнаёшь о проблеме раньше пользователей, а не от них.

### 3.3. Обновление движка

Ежедневный `pip install -U yt-dlp` + перезапуск воркеров. Обязательно
**фиксировать последнюю рабочую версию** и уметь откатиться: сломанные релизы
редки, но случаются.

**JS-runtime.** yt-dlp предупреждает: `No supported JavaScript runtime could be
found… YouTube extraction without a JS runtime has been deprecated, and some
formats may be missing`. Без `deno` в образе YouTube уже сейчас отдаёт неполный
список форматов, а со временем отвалится совсем. Это ровно тот случай из
раздела 1.2, когда площадка меняет правила, — ставится одной строкой в
`Dockerfile`, но заметить проблему без чтения логов невозможно.

### 3.4. Классификация ошибок

Не сваливать всё в «не получилось». Разделять и по-разному реагировать:

- `unsupported_site` — generic-extractor не справился → в Telegram, это кандидат на доработку
- `geo_blocked` / `login_required` — сообщить пользователю, ретрай бесполезен
- `rate_limited` / `captcha` — сигнал о проблемах с IP, приостановить очередь
- `network` — ретрай с backoff
- `disk_full` — критично, алерт немедленно

### 3.5. Мониторинг: Prometheus + Grafana

Grafana — панели и алерты, Prometheus — сбор и хранение метрик. Отдельным
слоем — Loki для логов, если захочется всё в одном интерфейсе.

#### 3.5.1. Экспортеры

| Экспортер | Что даёт |
|---|---|
| **node_exporter** | CPU, RAM, диск, сеть, load average, **температуры** |
| **cAdvisor** | ресурсы по контейнерам: кто именно ест память |
| **postgres_exporter** | соединения, размер БД, медленные запросы, блокировки |
| **redis_exporter** | память, длина очередей, hit rate кэша |
| **prometheus-fastapi-instrumentator** | RPS, latency по эндпоинтам, коды ответов |
| **Caddy** | встроенный `/metrics`, включается директивой `metrics` |

Температуры на ноутбуке — не декоративная метрика, а главная. Ставим
`lm-sensors`, отдаём через **textfile collector** у node_exporter. Алерт при
устойчивом превышении порога должен приходить раньше, чем машина уйдёт в
троттлинг или аварийное выключение.

#### 3.5.2. Прикладные метрики

Стандартных экспортеров мало — самое ценное придётся отдавать самому через
`prometheus_client`:

```
downloads_total{extractor, status}        counter
download_duration_seconds{extractor}      histogram
download_bytes_total{direction}           counter   -- in / out
queue_depth{state}                        gauge     -- queued / active
active_downloads                          gauge
disk_free_bytes                           gauge
ytdlp_version_info                        gauge     -- версия как label
extractor_failures_total{extractor,code}  counter
```

Ключевая из них — `extractor_failures_total`. Резкий рост по конкретному
экстрактору означает, что площадка сломалась, и узнаешь ты об этом за часы
до того, как канареечная проверка отработает по расписанию. Это делает
мониторинг не «красивыми графиками», а рабочим инструментом раздела 1.2.

#### 3.5.3. Панели

- **Железо** — CPU, RAM, диск, температуры, сеть
- **Сервис** — очередь, активные загрузки, latency API, коды ответов
- **Экстракторы** — доля успеха по площадкам за 24 часа, топ ошибок
- **Пользователи** — кто сколько скачал, кто упирается в квоты
- **Трафик** — входящий и исходящий по дням, прогноз исчерпания диска

#### 3.5.4. Алерты

Alertmanager с единым каналом в Telegram — туда же, куда идут канареечные
проверки и заявки на регистрацию:

| Условие | Приоритет |
|---|---|
| Диск заполнен больше 85% | критично |
| Температура выше порога 5 минут | критично |
| Сервис недоступен | критично |
| Postgres или Redis недоступны | критично |
| Доля ошибок экстрактора выше 50% за час | важно |
| Очередь не разбирается 15 минут | важно |
| Память выше 90% | предупреждение |

#### 3.5.5. Стоимость стека

Мониторинг занимает **500 МБ – 1 ГБ RAM**. При 8 ГБ на машине это укладывается
свободно, включая Loki. Настройки всё равно стоит выбрать умеренные:

- интервал сбора **30 секунд**, а не 5 — на старом CPU разница ощутима, а
  для наблюдения за домашним сервисом секундная гранулярность не нужна
- retention Prometheus **30 дней** с явным лимитом размера хранилища
  (`--storage.tsdb.retention.size`), чтобы метрики не съели раздел незаметно
- Loki подключать вторым шагом, после того как основной стек заработает

### 3.6. Журнал аудита и аварийный рубильник

**Аудит.** Раз в системе есть удаление учётных записей и прерывание чужих
задач, все административные действия пишутся в `audit_log`: кто, что, над кем,
когда, с какого IP. Просмотр — у суперадмина. Это не бюрократия: когда
что-то пропадёт, единственный способ понять причину — журнал.

**Рубильник.** Глобальные флаги в настройках, доступные суперадмину и
переключаемые без пересборки:

- `guest_access_enabled` — отключает анонимное скачивание
- `registration_enabled` — приостанавливает приём заявок
- `maintenance_mode` — очередь дорабатывает текущее, новые задачи не берутся

Первый флаг — прямой ответ на риск из раздела 4.5. Волна ботов или
подозрительная активность лечится одной галочкой, а не срочным деплоем ночью.

## 4. Требования к железу и размещение

### 4.1. Железо

Минимум для десятков загрузок в день:

- **CPU** — 2 ядра (при ремуксе; перекодирование потребует 4+ или NVENC/QSV)
- **RAM** — 2 ГБ минимум, 4 ГБ комфортно, 8 ГБ с запасом под мониторинг
- **Диск** — **SSD обязательно** под временные файлы, это горячая точка
- **Сеть** — главный ресурс, важнее процессора

**Фактическая конфигурация:** ноутбук Asus, 8 ГБ RAM, Samsung 870 EVO 512 ГБ
(SATA 2.5"), обслужен — термопаста заменена, продув сделан.

Потолок SATA III (~550 МБ/с) для этой задачи избыточен: канал закончится
задолго до диска. Железо из ограничения превратилось в запас.

### 4.2. Подготовка ноутбука

- Ubuntu Server, всё в Docker Compose — переезд на другое железо будет бесплатным
- `/etc/systemd/logind.conf`: `HandleLidSwitch=ignore` — иначе уснёт с закрытой крышкой
- Термопаста и продувка **до** запуска: машине много лет, а работать будет нонстоп
- Мониторинг температуры + автоалерт при перегреве

#### 4.2.1. Разметка диска (512 ГБ)

| Раздел | Размер | Точка монтирования | ФС | Назначение |
|---|---:|---|---|---|
| ESP | 512 МБ | `/boot/efi` | vfat | загрузчик (только для UEFI) |
| swap | 8 ГБ | — | swap | страховка от OOM-killer |
| Система | 100 ГБ | `/` | ext4 | ОС, Docker, Postgres, Prometheus |
| Данные | остаток (~366 ГБ) | `/srv/media` | ext4 | скачанные файлы, кэш |

**Зачем отдельный раздел под данные.** Это единственная директория, которую
наполняют пользователи, и единственная, которая реально может заполниться. На
общем разделе переполнение уронит всё сразу: Postgres перестанет писать
транзакции, Docker — логи, Prometheus — метрики, и разбираться придётся с
мёртвой машиной. На отдельном — заполнится только `/srv/media`, сервис
корректно встанет на паузу по своей же проверке свободного места (раздел 3),
а система, БД и мониторинг продолжат работать и покажут, что произошло.

Замечания:

- **Если машина с legacy BIOS, а не UEFI** — раздел ESP не нужен, вместо GPT
  используется MBR. Проверить: `[ -d /sys/firmware/efi ] && echo UEFI`.
- **ext4 резервирует 5% под root.** На разделе данных это ~18 ГБ впустую:
  `tune2fs -m 1 /dev/sdaX` возвращает большую часть.
- **`noatime`** в `/etc/fstab` для раздела данных — лишние записи при каждом
  чтении файла на SSD не нужны.
- **LVM** вместо жёстких разделов, если хочется менять пропорции потом.
  Гибкость в обмен на лишний слой; для одной машины с понятным профилем
  нагрузки — скорее избыточно.
- **Docker хранит образы и тома в `/var/lib/docker`** (раздел `/`). 100 ГБ
  хватает с запасом, но `docker system prune` стоит поставить в cron.
- **Файлы загрузок монтировать в контейнеры bind-mount'ом** с `/srv/media`,
  не именованным томом — иначе они уедут обратно на системный раздел.

#### 4.2.2. Настройки SSD

- `systemctl enable fstrim.timer` — TRIM по расписанию
- `vm.swappiness=10` в `/etc/sysctl.d/` — swap как страховка, а не как
  рабочий инструмент
- Алерты по свободному месту: **85% на `/srv/media`**, **90% на `/`** —
  два отдельных правила, у них разная критичность
- SMART-мониторинг: `smartd` плюс сбор атрибутов в Prometheus, чтобы износ
  диска был виден заранее

### 4.3. Сетевой доступ

**Вводные:** IP статический, порты 80 и 443 снаружи уже заняты, сервис будет
жить на кастомном порту. DDNS не нужен.

Отсюда следует единственное значимое требование: **сертификат выпускается
через DNS-01 challenge**. Проверки HTTP-01 и TLS-ALPN обе требуют 80/443, и
обе отпадают. DNS-01 подтверждает владение доменом через TXT-запись, порты не
нужны вообще.

Caddy это умеет, но нужен модуль под конкретного DNS-провайдера — сборка
`caddy-dns/<провайдер>` и API-токен с правом менять записи. Токен ограничить
одной зоной.

```
video.example.com:8443 {
    tls {
        dns <провайдер> {env.DNS_API_TOKEN}
    }
    encode zstd gzip
    metrics /metrics
    reverse_proxy api:8000
}
```

Что учесть:

- **Порт в адресе никуда не денется** — пользователи будут ходить на
  `https://video.example.com:8443`. Для PWA это не проблема, но в приглашениях
  и боте ссылку давать целиком.
- **Корпоративные и мобильные сети иногда режут нестандартные порты.**
  Если кто-то из друзей не сможет зайти — причина, скорее всего, в этом.
  Выбирай порт из привычного диапазона (8443, 9443), а не случайный.
- **Проверить, что роутер пробрасывает выбранный порт на ноутбук**, и что он
  не конфликтует с уже проброшенными восемью.
- **Автопродление сертификата** тоже пойдёт через DNS-01 — токен должен
  оставаться валидным, иначе через 90 дней всё встанет. Мониторить срок
  жизни сертификата отдельной метрикой.

**Cloudflare Tunnel не рекомендуется:** условия бесплатного тарифа ограничивают
раздачу больших нехтмл-файлов через их прокси, видеофайлы — ровно этот случай.

**Tailscale** остаётся вариантом, если решишь отказаться от публичного доступа
совсем: сервис виден только внутри приватной сети, снаружи его нет физически.

**Cloudflare Tunnel не рекомендуется:** условия бесплатного тарифа ограничивают
раздачу больших нехтмл-файлов через их прокси, видеофайлы — ровно этот случай.

**Tailscale** — хороший вариант, пока круг пользователей ограничен семьёй и
друзьями: сервис виден только внутри приватной сети, снаружи его нет физически.

### 4.4. Доступ и аутентификация

Регистрация — **только через заявку в Telegram-боте с ручным одобрением**
(см. 2.6). Публичной формы signup нет.

Сессионные cookie для веба, JWT — когда дойдёт до нативных клиентов.

**Отдельно про гостевой доступ.** Анонимное скачивание на публичном адресе —
самая уязвимая часть замысла. Лимит «5 в сутки» считается по IP, а IP меняется
одним кликом; после индексации поисковиками адрес находят боты. Платит за это
офисный канал и IP-репутация у площадок.

Гостевой режим стоит оставить, но с тремя предохранителями:

1. **Cloudflare Turnstile** на анонимной форме — бесплатно, не требует
   проксирования трафика через Cloudflare (только JS-виджет), отсекает
   основную массу автоматики.
2. **Флаг `guest_access_enabled`** (см. 3.6) — отключение одной галочкой.
3. **`noindex`** в robots.txt и мета-теге. Незачем попадать в выдачу.

Гостевые лимиты считать по связке «IP + отпечаток браузера», а не по одному
IP — за общим офисным NAT иначе все пользователи делят одну квоту на всех.

### 4.5. Юридическая рамка

Локальная программа — инструмент пользователя. Публичный сервис — это уже
savefrom/Televzr со всеми последствиями: жалобы правообладателей, снос
хостером, отказы платёжных провайдеров. Именно поэтому Televzr отправляет
ставить десктопное приложение вместо решения задачи на своей стороне.

Для закрытого круга риск принципиально другой. Держать сервис приватным — это
не только техническое, но и правовое решение.

### Этап 2. Прогресс и надёжность (1–2 выходных)

- [x] `progress_hooks` → Redis pub/sub → SSE-эндпоинт
- [x] Статусы задач, отображение прогресса в UI
- [x] Классификация ошибок (раздел 3.4), понятные сообщения пользователю
- [x] Ретраи с backoff, таймауты задач
- [x] Логирование, `docker compose logs` в читаемом виде

**Что выяснилось на практике:**

- **Прогресс считается по задаче, а не по потоку.** DASH качается двумя
  проходами — сначала видео, потом звук, — и каждый рапортует свои 0–100%.
  Полоска дважды добегала до конца. Считаем сумму по всем потокам от
  ожидаемого размера, делаем монотонной (оценка неточна, и на стыке потоков
  процент дёргался назад) и упираем в 99%: сотня принадлежит `ready`.
- **Ремукс не шлёт ни одного события прогресса.** Пока работает ffmpeg,
  полоска молча стоит на последних процентах — выглядит как зависание. Начало
  ремукса ловится отдельным шаблоном `postprocess:` и переводит задачу в
  `processing`, который для этого и был зарезервирован.
- **`text/event-stream` нельзя отдавать через общий `encode`.** Caddy по
  умолчанию сжимает всё `text/*`, и SSE копится в буфере вместо того, чтобы
  идти в браузер по событию. Список типов задан явно, у `reverse_proxy`
  выставлен `flush_interval -1`.

### Этап 3. Развилка форматов (выходные)

Главная оптимизация нагрузки — раздел 1.5.

- [x] `GET /api/formats?url=…` — список доступных вариантов с кэшем в `url_meta`
- [x] Профили качества (таблица 2.7) вместо сырых селекторов yt-dlp

- [x] Ремукс через ffmpeg `-c copy` для DASH

- [ ] Стриминг без промежуточного файла (fragmented MP4) — опционально

**Что выяснилось на практике:**

- **YouTube больше не отдаёт progressive-форматы.** У проверенных роликов их
  ноль: раздельные видео- и аудиодорожки во всех разрешениях. Оценка раздела
  1.5 «отсекает больше половины запросов» для YouTube не работает — там всегда
  ремукс. Оптимизация всё равно окупается, но на другом классе источников:
  прямые ссылки на файлы и мелкие площадки, то есть ровно на вебинарах.
- **Generic-экстрактор не размечает форматы вообще.** Одиночный файл приходит
  без высоты, кодеков и размера, поэтому селекторы с `[height<=N]` его не
  выбирают, а список качества оказывается пуст. Лечится хвостовым `/b` в
  селекторе и отдельной строкой «Исходное качество».
- **Прямую ссылку можно отдавать только при `protocol` = http/https.** Манифест
  HLS или DASH — не файл: браузер скачает текстовый плейлист вместо видео.
- **Записи трансляций YouTube режет до 720p** независимо от JS-runtime. Если
  качество кажется низким, сначала проверь `was_live`.

### Этап 4. Роли и квоты (1–2 выходных)

- [x] Таблицы `roles`, `quota_profiles`, `users` с ролью
- [x] Аутентификация, сессии, принудительная смена пароля
- [x] Token bucket в Redis — единая механика для всех ролей
- [x] Суточные счётчики, глобальный семафор поверх ролевых квот
- [ ] Гостевой режим: отпечаток (**готов**), Turnstile, `noindex`
- [x] Защита входа от перебора
- [ ] История загрузок пользователя
- [ ] TTL файлов, cron-чистка, контроль свободного места

**Что выяснилось на практике:**

- **Ведро и суточный счётчик обязаны проверяться одной операцией.** Если
  списать токен, а потом упереться в суточный лимит, списание надо
  откатывать — и этот откат теряется при любом сбое между двумя запросами.
  Оба лимита живут в одном Lua-скрипте: суточный проверяется первым и растёт
  только вместе с выданным токеном.
- **Параллельный лимит считается по БД, а не счётчиком в Redis.** Счётчик
  пришлось бы уменьшать в каждой ветке завершения, включая падение воркера,
  и он неминуемо разъехался бы с действительностью. `SELECT count(*)` по
  нетерминальным статусам всегда говорит правду.
- **У полного ведра время должно стоять.** Иначе простой копится как долг:
  вернувшись через сутки, пользователь получает токен «задним числом», а
  ведро оказывается пустым сразу после первой загрузки.
- **Справочник ролей заполняет приложение, а не миграция.** Лимиты правятся
  из админки, поэтому цифры в SQL-файле стали бы вторым источником истины и
  разошлись бы с базой после первой правки. `ensure_roles` только дополняет
  недостающее и никогда не переписывает существующие строки — перезапуск API
  не откатывает вчерашнюю правку квот.
- **Пароль суперадмина из `.env` не восстанавливается при перезапуске.**
  Учётка создаётся один раз; дальше `.env` её не трогает, иначе смена пароля
  отменялась бы каждым рестартом. Файл на диске знает не только владелец —
  отсюда `must_change_password` с самого начала.
- **`docker compose restart` не перечитывает `env_file`.** Новые переменные
  подхватывает только пересоздание контейнера (`up -d --force-recreate`);
  на этом легко потерять полчаса, глядя в правильный `.env`.
- **Сессия живёт в Redis, а не в подписанном токене.** JWT нечем отозвать, а
  выкидывать пользователя нужно уметь: смена пароля обязана обрывать
  украденную cookie, иначе она бессмысленна. Второй ключ со списком токенов
  пользователя существует ровно ради этого — иначе пришлось бы перебирать всю
  базу Redis.
- **Смена пароля не должна выкидывать того, кто её сделал.** Сессии сбрасываются
  все, но текущему устройству сразу выдаётся новая cookie.
- **Неудачный вход отвечает одинаково** на «нет такого адреса» и «пароль не
  тот», а несуществующий email сверяется с фиктивным хешем: разное время
  ответа превращает форму входа в список учётных записей.
- **Счётчик неудач считает логин без учёта регистра.** Иначе перебор идёт по
  `Root@`, `rOot@`, `ROot@` и ни разу не упирается в блокировку.

**Критерий готовности:** гость упирается в свои 5, пользователь — в 16,
суперадмин не упирается ни во что.

## 6. Чего не делать

| Не делать | Почему |
|---|---|
| Писать свои экстракторы | yt-dlp покрывает задачу; поддержка съест всё время |
| Перекодировать по умолчанию | самая дорогая операция, нужна редко |
| Оставлять качество по умолчанию на «максимуме» | 4K-ролик — это ~1.4 ГБ канала в обе стороны вместо 300 МБ |
| Пускать сырой селектор yt-dlp из API наружу | произвольное выражение в `-f` от пользователя; наружу — только профили 2.7 |
| Отдавать файлы через Python | это работа веб-сервера, Caddy делает это эффективнее |
| Открывать публичную регистрацию | боты, трафик, IP-репутация, юридические риски |
| Держать сервис на VPS | датацентровые IP режут быстро |
| Строить микросервисы | монолит + воркеры полностью закрывают задачу на этом масштабе |
| Оптимизировать до появления проблемы | сначала лимиты, потом измерения, потом оптимизация |
| Зашивать квоты в код | правка цифр не должна требовать пересборки |
| Давать админу право менять роли | иначе он становится суперадмином за два клика |
| Отдавать гостевой доступ без Turnstile и рубильника | публичный адрес находят боты |
| Ставить Grafana на 2 ГБ RAM | стек съест половину памяти; сначала апгрейд |
| Собирать метрики раз в 5 секунд | на старом железе разница в нагрузке кратная |

## 7. Ориентировочные сроки

Объём вырос: добавились ролевая модель, админка, Telegram-бот и мониторинг.
При работе «в перерывах между» — примерно **4–5 месяцев** до полного состава.

Но пользоваться можно гораздо раньше: **этапы 0–4 (примерно 6–8 выходных)**
уже дают работающий сервис с квотами и учётными записями. Админка, бот и
Grafana — это удобство эксплуатации, а не условие запуска. Заводи пользователей
руками через `psql`, пока не дойдут руки до пятого этапа.

Порядок этапов 5–8 при желании можно менять. Единственное, что я бы не
откладывал далеко, — мониторинг: он окупается первой же аварией, а на старом
ноутбуке она обязательно случится.

Самая недооценённая статья расходов — не разработка, а **поддержание
работоспособности** после запуска. Закладывать на это несколько часов в месяц
как постоянную величину.
